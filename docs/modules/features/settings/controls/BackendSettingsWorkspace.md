# BackendSettingsWorkspace

Source: `src/features/settings/controls/BackendSettingsWorkspace.ts`
Owner: `feature.settings-shell`
Updated: 2026-11-09

Shared workspace chrome for all six selectable backends. It explains that plugin defaults belong to the current vault and that save success does not prove runtime application. `renderBackendSettingsWorkspace` retains the source/application strip and native recovery disclosure for the five other backends. DSH uses a purpose-named `Connection backup and restore` variant; `SettingsDshSection.renderTab` keeps it only below Connection and removes the repeated bar on the other three subtabs. Workspace markers and the separately mounted missing-program guidance remain on all pages.

`captureBackendRecoveryPoint` records only the backend-specific non-secret allowlist. `saveBackendRecoveryPoint` persists a user-marked working default set under `backendSettingsRecoveryPoints`; failed persistence restores the prior recovery map. `readBackendRecoveryPoint` treats persisted records as untrusted and validates the version, timestamp and allowed keys. A modified recovery record cannot add credentials, environment variables or unknown properties to a backend.

`restoreBackendRecoveryPoint` normalizes and mutates the chosen backend object in place. This preserves the live reference held by Claude query builders and avoids replacing other adapters' settings objects. It rolls memory back if saving fails. The renderer then replays Codex's existing runtime mutators and refreshes the surface. Connection-path changes still require the boundary shown on their fields; the UI never marks backend confirmation based on the local snapshot.

Recovery takes two actions from the workspace: open the recovery disclosure, then restore. For DSH, the closed summary shows `No backup yet` or its saved timestamp. The body names the four existing allowlisted fields (program path, working directory, profile, transport), exclusions and current-vault/single-backup scope. Save changes to Update after success and immediately refreshes the timestamp and restore availability; updating replaces the one stored point. Saving never tests a connection. Restored DSH values apply on the next connection, with plugin reload guidance for changed program paths. Buttons stay disabled while pending; local polite feedback distinguishes save/restore progress and generic error text, preserving prior settings/backup on failure. The other backend variants keep their existing working-default wording. Keys, environment values, raw configuration overlays and native files retain their own storage and archives. The selected non-secret defaults are the scope of this checkpoint, not a second copy of every external configuration source.

An explicitly configured absolute executable path that no longer exists adds an actionable missing-program state on every workspace. Users can restore automatic discovery without losing model or permission defaults. Failed persistence restores the original path; bare command names and automatic discovery remain the backend resolver's responsibility, so the shared component does not pretend to validate PATH or backend compatibility.

Behavior coverage: `tests/unit/features/settings/BackendSettingsWorkspace.test.ts` verifies scope filtering, secret exclusion, per-backend identity preservation, save/restore failures, serialized retention, injected-key rejection and the restore action path. Live Test Vault verification must additionally prove actual persisted reload and the corresponding runtime application boundary.
