# BackendSettingsWorkspace

Source: `src/features/settings/controls/BackendSettingsWorkspace.ts`
Owner: `feature.settings-shell`
Updated: 2026-11-12

Claude Code, Codex, Pi and ZCode receive the `opencodian-backend-task-workspace` marker on every task. The module-local `TASK_WORKSPACE_BACKENDS` set holds that layout opt-in; OpenCode 2 and DSH remain outside it. The separate `renderBackendTaskHeading` helper accepts the resolved label and renders a 25px serif heading only for that marker, ahead of missing-installation guidance. This keeps the recovery renderer's existing four-parameter contract. The marker scopes the transparent DSH A form and framed recovery disclosure. Recovery persistence and missing-executable behavior are unchanged.

After the backend section mounts, `finalizeBackendTaskWorkspace` keeps the source/application note and recovery disclosure only below Connection (or ZCode Installation), removing that bar from all other four-backend tasks while retaining their layout marker. If the shared task H2 exists, it removes owner-rendered H3/H4 headings whose complete trimmed text duplicates it, including Pi's model title, ZCode's chat title and Codex's conversation-defaults group title. Distinct group headings remain, as do headings in classic/direct mounts without the shared H2. OpenCode 2 and DSH do not enter this finalization path.

DSH and OpenCode 2 use purpose-named, initially collapsed connection backup variants without the repeated shared source/application strip. Their section owners place the existing bar after Connection and omit it from other task pages. OpenCode 2's title and body explicitly name its three allowlisted fields (connection mode, executable path, default permission mode); server address, credentials, provider/model/agent/MCP settings and the JSONC overlay are excluded. DSH retains its separate four-field allowlist and copy. Workspace markers and the separately mounted missing-program guidance remain on all pages. The other four backends retain their working-default wording at the connection footer described above; none of these surfaces treats save success as runtime confirmation.

`captureBackendRecoveryPoint` records only the backend-specific non-secret allowlist. `saveBackendRecoveryPoint` persists a user-marked working default set under `backendSettingsRecoveryPoints`; failed persistence restores the prior recovery map. `readBackendRecoveryPoint` treats persisted records as untrusted and validates the version, timestamp and allowed keys. A modified recovery record cannot add credentials, environment variables or unknown properties to a backend.

`restoreBackendRecoveryPoint` normalizes and mutates the chosen backend object in place. This preserves the live reference held by Claude query builders and avoids replacing other adapters' settings objects. It rolls memory back if saving fails. The renderer then replays Codex's existing runtime mutators and refreshes the surface. Connection-path changes still require the boundary shown on their fields; the UI never marks backend confirmation based on the local snapshot.

Recovery takes two actions from the workspace: open the recovery disclosure, then restore. For DSH, the closed summary shows `No backup yet` or its saved timestamp. The body names the four existing allowlisted fields (program path, working directory, profile, transport), exclusions and current-vault/single-backup scope. Save changes to Update after success and immediately refreshes the timestamp and restore availability; updating replaces the one stored point. Saving never tests a connection. Restored DSH values apply on the next connection, with plugin reload guidance for changed program paths. Buttons stay disabled while pending; local polite feedback distinguishes save/restore progress and generic error text, preserving prior settings/backup on failure. OpenCode 2 reuses the same disclosure anatomy, pending/error handling and timestamp refresh with scoped `settings.opencode2.backup.*` copy. The four remaining backend variants keep their existing working-default wording. Keys, environment values, raw configuration overlays and native files retain their own storage and archives. The selected non-secret defaults are the scope of this checkpoint, not a second copy of every external configuration source.

An explicitly configured absolute executable path that no longer exists adds an actionable missing-program state on every workspace. Users can restore automatic discovery without losing model or permission defaults. Failed persistence restores the original path; bare command names and automatic discovery remain the backend resolver's responsibility, so the shared component does not pretend to validate PATH or backend compatibility.

Behavior coverage: `tests/unit/features/settings/BackendSettingsWorkspace.test.ts` verifies scope filtering, secret exclusion, per-backend identity preservation, save/restore failures, serialized retention, injected-key rejection, the restore action path, four-backend layout scoping and the separate OpenCode 2 backup scope. Live Test Vault verification must additionally prove actual persisted reload and the corresponding runtime application boundary.
